DOCUMENTATION / DISTRIBUTED BUILDS

Build with the machines you already have.

Install a lightweight service on a host, discover and pair it from your controller, then let Main{Create} manage its GitHub Actions runner. Start with Raspberry Pi OS 64-bit for the first end-to-end test.

Alpha software. The Linux ARM64 installer and controller-managed runner provisioning are implemented for homelab testing, but fresh-device pairing, automatic runner registration, and reboot recovery still need physical acceptance testing. There is no public hosted controller or universal installation endpoint.

01 · PREPARE

Prepare your build machine

Choose a platform below. These tabs describe platform readiness; they do not imply that every installer is already released.

Alpha installer available

Raspberry Pi OS Lite (64-bit)

  1. Install Raspberry Pi Imager on your computer and choose the Pi model.
  2. Choose Raspberry Pi OS Lite (64-bit) as the image and your microSD card as the target. Imaging erases the selected card—back up any important files first.
  3. Under Imager’s OS customisation, set a distinct hostname (for example maincreate-pi-builder), a Linux username and password, network settings if necessary, and enable SSH with password authentication.
  4. Write the image, put the card into the Pi, connect network and power, then SSH into the host using the credentials you just created. For your first test, a wired connection reduces discovery problems.
ssh <linux-user>@maincreate-pi-builder.local

If .local does not resolve across your network, use the Pi's IP address instead. The Pi needs to reach the controller's trusted HTTPS endpoint.

Native installer planned

Linux x64

Keep a supported Linux distribution updated and enable network connectivity. A dedicated Linux x64 release package, one-command installer, and validation are not yet provided. Do not run the ARM64 installer on an x64 machine.

The existing JavaScript development Host Service may be used for experimental enrollment with Node.js 22+, but it is not equivalent to the native managed runner workflow.

Native installer planned

macOS

Prepare a Mac with a compatible macOS version and Xcode if you want Apple application builds. The native launchd installer and controller-managed GitHub runner adapter are not part of the Linux ARM64 alpha. Do not use the Pi installation command.

Projects requiring Xcode will remain unmatched until a compatible managed macOS runner is online and reports that toolchain.

Native installer planned

Windows x64

A Windows Service installer and managed GitHub runner provisioning flow are planned. The Linux ARM64 binary and systemd setup do not work on Windows.

Windows-specific toolchain inventory and verified unattended setup will be documented when released.

02 · INSTALL

Install the Host Service

Once the Pi is running and you have signed in through SSH, supply the HTTPS address of your own Main{Create} controller. The installer comes from that controller, not from this marketing website.

Enter the trusted controller URL to generate your one-command install.

Enter your controller URL above.

Installation requests sudo, installs Avahi and OpenSSH as needed, downloads the Linux ARM64 Host Service, verifies the provided checksum, and enables maincreate-host.service. It does not register a GitHub runner yet.

systemctl status maincreate-host --no-pager
03 · ENROLL

Discover and pair the builder

  1. Sign in to your Main{Create} controller's admin portal. Go to Builders → Add a Build Machine.
  2. Choose Find nearby hosts (mDNS). If discovery is unavailable, enter the Pi's hostname.local or its IP address manually. mDNS generally does not traverse VLANs or container bridges without additional networking.
  3. Click Read SSH fingerprint. On the Pi, independently read the key fingerprint with the command below and confirm it matches. Do not proceed if they differ.
  4. Enter the Pi's local Linux username and password from Raspberry Pi Imager, not your Main{Create} portal password. Select Pair this host. The controller performs one SSH pairing and the host stores a unique management credential.
ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub

The portal does not retain your Linux password after pairing. The enrolled host connects outbound over HTTPS. Initial pairing requires SSH from controller to Pi on TCP port 22.

04 · PROVISION

Let the controller configure GitHub Actions

  1. Wait until the paired host is listed as Online in Builders. Its operating system, architecture, and detected tools should appear.
  2. In the host's Manage column, select Provision GitHub runner.
  3. Main{Create} uses the selected GitHub organization to request a short-lived runner registration token, assigns labels from detected capabilities, and instructs the host to install the official runner. The Pi does not need permanent GitHub credentials.
  4. Confirm that the runner appears in GitHub's organization Actions runner list, and check the Host provisioning activity panel for completion. Then reboot the Pi and verify both the Host Service and runner return online.
Access requirement: the connected GitHub App and authorized account must be allowed to manage organization self-hosted runners. GitHub can reject provisioning when that permission has not been granted. A successful controller action alone does not prove a real workflow build passed.
05 · SOURCE

Connect a GitHub organization

In the controller, use Settings → GitHub Connection. Complete GitHub authorization, select an organization where the Main{Create} GitHub App is installed, and ensure repository access is available. Main{Create} synchronizes accessible repositories automatically.

Read access to repository contents is needed for workflow and project-requirement detection. Managing self-hosted runners is a separate permission. You do not enter GitHub tokens on each builder.

06 · COVERAGE

Track project requirements automatically

Main{Create} can infer some requirements from GitHub Actions workflows. To pin OS, architecture, and SDK versions reliably, add an optional .maincreate/project.json file to a repository:

{
  "schema": 1,
  "targets": [
    {
      "os": "linux",
      "arch": "arm64",
      "tools": [
        { "name": "esp-idf", "version": "5.5.x" }
      ]
    }
  ]
}

Requirements are alternatives across targets and additive within each target. Active projects with no matching online managed runner get a quiet in-app notice. Projects whose requirements cannot be detected show Unknown, not a false incompatibility. You can ignore a project’s alerts without deleting it.

07 · VERIFY

Troubleshooting your first builder

Pi does not appear in discovery

Check that the Host Service and Avahi are running and the Pi is on a reachable network. mDNS may not cross VLANs or reach the controller container. Use the Pi IP address to pair manually.

avahi-browse -rt _maincreate._tcp
Host fails to pair or the fingerprint changes

Ensure SSH password authentication is enabled for the Pi's user and the controller can reach TCP/22. Independently verify the Ed25519 fingerprint from the Pi's local SSH host key. A changed fingerprint can indicate re-imaging or an unexpected device; investigate before proceeding.

Host is paired but offline

Confirm outbound HTTPS access to your controller, certificate trust, DNS resolution, and service logs. Pairing alone does not imply the heartbeat is healthy.

journalctl -u maincreate-host -n 80 --no-pager
GitHub runner registration fails

Check the controller’s Host provisioning activity, its GitHub organization selection, and GitHub App runner permissions. Do not manually register a second Actions runner on the Pi to work around an incomplete controller action.

Never post the contents of /var/lib/maincreate/host.json: it contains a private host credential.
